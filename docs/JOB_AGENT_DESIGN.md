# Job search and application agent

Product direction agreed 2026-09-16: collect suitable openings, explain the shortlist, ask for the user's selection, prepare the exact application, and submit only within that authorization. A persistent application workflow coordinates tools inside this project. Codex skills remain development aids.

## User journey

1. Configure target roles, geography and company sources once.
2. Collect public jobs, normalize descriptions, deduplicate by provider/board/posting ID, and retain the source URL plus description fingerprint.
3. Present a shortlist with preference fit, then evidence-based semantic assessment. Never present a preference score as an interview probability.
4. Record save, dismiss, or approve decisions against the exact posting snapshot.
5. Prepare approved applications with the verified profile and Gemini, validate claims, and retain the generated change-set reference.
6. Present the resume and application answers together for review. Existing sentence review remains the first implementation; a consolidated review can replace its UX only after equivalent content-bound approval is implemented.
7. Build and verify the exact approved DOCX, attach it to the correct application, and fill supported real ATS forms.
8. Bind final authorization to destination, posting, resume bytes and final answers. Execute once and record a receipt; an uncertain network outcome must be reconciled, never blindly submitted again.

## First increment implemented

- `/agent`: a real, locally persisted job inbox, preferences, source health, decisions and preparation progress.
- `/api/agent`: closed commands for configure, search, assess, decide and prepare; same-origin mutation checks use the browser-facing Host, not an internal Next.js hostname.
- Greenhouse public job-board GET and Lever public posting GET adapters. Fixed API hosts, board-token validation, redirect refusal, request deadlines, bounded response size, Lever pagination and complete-feed validation.
- Starter boards: Spaceium, Wealthsimple, AltaML and Achievers. These are a small editable seed list, not a Canada-wide job index. Optional Brave source discovery can expand the list after user confirmation.
- Default locations: GTA municipalities, Ottawa and Kingston. Generic remote roles are excluded by default. Roles remain configurable; software engineering, AI and ML are starting preferences, not inferred work-authorization eligibility.
- Transparent role/location filtering; explicit title exclusions; original posting age and sponsorship are not guessed.
- Optional Gemini evidence assessment cites verified, non-conflicted, normal-sensitivity facts for each requirement and highlights partial/missing support. Model coverage is not a qualification guarantee. Unknown citations or incomplete requirement coverage are rejected; profile/posting changes mark saved assessments stale.
- Stable provider posting identity preserves decisions on repeated searches. A changed description, title, location or URL invalidates prior authorization. Failed feeds never mark jobs closed; only complete successful scans can do so.
- Approving creates a durable preparation task. The UI immediately continues through idempotent JD import and the existing Gemini resume generator. No key, no verified identity, or failed claims produces a retained, retryable blocked task.
- Resume Studio links include the exact change-set ID so concurrent applications cannot open the latest unrelated resume by mistake.
- Preparation has a five-minute lease. A restart can be recovered by retry after expiry. An in-flight cancellation/reapproval invalidates the attempt token; its late result cannot advance the task.
- Local decision history is retained separately from the active task. Completed proposal retries do not regenerate or erase sentence reviews.

The first increment stops at resume review. No real application is submitted. Search runs on demand; there is no scheduler, persistent background worker, or claim of 24/7 operation yet.

## Components and records

| Component | Input | Output / persistence |
|---|---|---|
| Source adapters | Company board configuration | Complete normalized public feed or explicit source error |
| Discovery | Feed snapshots + preferences | Jobs, fingerprints, availability, search runs |
| Matching | JD requirements + verified normal-sensitivity facts | Cited support, missing requirements, uncertainty |
| Decisions | User action + expected fingerprint | Append-only decision record and current preparation authorization |
| Orchestrator | Approved candidate + task state | Imported job ID, change-set ID, checkpoint or failure |
| Resume generation | Verified profile + parsed JD | Existing Gemini proposals and both claim reports |
| Artifact builder | Content approval | DOCX + existing render gates + manifest |
| ATS runner (next) | Approved document + scoped answer plan | Form snapshot, write verification, receipt |

Discovery and tasks live in the existing local JSON storage, under `RESUME_AGENT_DATA_DIR` or the dashboard `.data` directory. Existing single-process write serialization and atomic replacement apply. This is suitable for one local dashboard process. Before introducing concurrent workers, migrate to a transactional store with unique posting/task keys, durable leases, per-step idempotency keys, outbox dispatch and append-only events. Do not stretch the in-process mutex into a multi-process queue.

### STORE-01 bounded Windows replacement recovery

On 2026-09-24 the pre-fix targeted storage/execution run reproduced two EPERM failures at JSON rename (70 tests passed, 2 failed). This confirms the failing operation, not the identity of a locking process or an antivirus cause. Upstream [libuv's Windows rename implementation](https://github.com/libuv/libuv/blob/v1.x/src/win/fs.c) performs a replacement and reports the OS error; [Node's issue tracker](https://github.com/nodejs/node/issues/29481) also documents Windows replacement failures. These references are context, not proof of this machine's underlying cause.

`atomic-json-write.ts` now opens a UUID-named sibling staging file exclusively, writes validated serialized JSON once, closes its handle and renames it into place. Only Windows EPERM/EBUSY rename errors get four bounded delayed retries (20, 50, 100, 200 ms: 370 ms total scheduled waiting, excluding filesystem operation time). The source, destination and prepared bytes stay identical. No callback, browser fill, upload, writeFile, permission change or delete/copy fallback is retried. Other failures and exhausted retries propagate. The existing global in-process write queue remains held through replacement; update captures one absolute target before reading/mutating, so a configuration change during the callback cannot move that transaction.

Cleanup attempts to remove only the staging file successfully created by this operation; cleanup failure neither hides a primary error nor reports an already committed record as failed. Existing records and legacy staging files are not deleted to force success. Abandoned staging files are never automatically promoted and remain ordinary unencrypted local data. This is an atomic-visibility improvement, not multi-process locking, encryption, fsync/power-loss durability, or new application authority.

Regression coverage adds 27 tests: 18 injected-I/O atomic-write cases, 7 real-filesystem store cases (including 200 queued updates), and 2 ATS persistence-boundary cases. They verify bounded retry, persistent failure preserving old bytes, one callback per update, queue release/ordering, original-directory binding, no stale staging reuse, and no browser write when spent-consent persistence fails. A failed receipt save after a browser write leaves the attempt stopped/consumed and never repeats that write. No P6 rendering implementation, browser adapter or user data was changed.

Post-fix full dashboard verification passed in both default parallel mode and `--no-file-parallelism --maxWorkers=1`: each run had 419 passed, 3 opt-in live skipped, across 24 files. Dashboard typecheck and production build also passed. This supersedes the earlier failing test-run status, not the unresolved attribution of the OS-level transient failure or the outstanding real-site application gates. No desktop UI or real-provider acceptance was performed in this storage-only increment.

It requires a current approved/open canonical Greenhouse posting, verifies the public form, opens one ephemeral browser, then verifies the public schema and local approval again before returning anything. A cancellation, changed approval/posting/schema, custom URL or unexpected page URL refuses the result. Nothing is persisted and no profile/answer data is loaded.

The new `@resume-agent/browser-runner/greenhouse-observer` subpath is separate from the existing fixture runner. It uses the existing policy gate for opening and snapshot reads, with the exact current origin. Chromium has a fresh context, no saved login/profile, blocked service workers and disabled downloads. Request interception permits only GET of the exact canonical posting and versioned JS/CSS under the fixed Greenhouse presentation CDN. Redirect following is disabled; non-GET, arbitrary API/third-party resources, child-frame navigation and WebSockets are refused. Reads are bounded by launch/navigation deadlines, a 30-second browser lifetime, 80 requests, 8 MB response and 30 MB cumulative buffered-response checks. Response limits are checked after buffering when a source omits Content-Length; this is not a streaming memory sandbox. All browser resources close on success/failure. There are no click/fill/upload/submit methods or reusable session handles.

The owned extraction script emits at most 300 controls with bounded structural IDs, names, labels, types, required/disabled/visible flags and option labels. It does not emit input values, selected/checked state, raw HTML, scripts, cookies, screenshots or answer hashes. A second sample detects immediate hydration drift, not future stability. Detected login/MFA, CAPTCHA/access checks or closed-posting text stop further sampling; frames, custom controls, truncation and restricted network are explicit limits. The adapter never solves access checks or expands permissions to load a blocked resource.

Reconciliation requires unique exact DOM names/IDs (including the known `job_application[field]` wrapper), normalized label/type and required agreement. Shared identifiers, mismatched or hidden/disabled controls, unobserved alternatives/options and custom widgets remain ambiguous/missing/manual. Extra controls, including submit buttons, are listed without executable locators. Even a corresponding control is observational evidence only: `canFill` and `canSubmit` remain false. Since third-party resources are blocked and no controls are clicked, conditional questions and complete custom-option lists are not claimed as observed.

### JA-03c Gemini narrative answer preparation

`/api/agent/answers` adds closed same-origin generate/review/delete commands and an uncached local GET. Generation uses the existing native Gemini adapter/key configuration, not a new provider gateway. With no key, generation fails before a public fetch. Loading saved drafts makes no model call. The page never sends candidate values to the ATS.

Only clearly recognized ordinary English narrative questions with a single known text control are eligible. Identity/contact, eligibility, protected attributes, compensation, legal/consent, attachments, options, alternative/unknown controls and instruction-like questions remain manual. Model context contains only question metadata and verified, non-conflicted, normal-sensitivity employment/achievement/skill/project/education fact IDs and values; private, credential-like and contact text is filtered. This narrow regex routing is conservative, not exhaustive semantic classification.

One bounded structured-output model call must cover every eligible question exactly once. Duplicate/unknown/missing questions or malformed output fail the plan. Unknown/duplicate fact citations, low confidence, unsupported claim-bearing wording/numbers or unsafe text downgrade the answer to manual; discarded text is not displayed. The existing local grounded-wording guard is not a full semantic verifier: reviewers must check relevance and meaning. Generation checks the exact approved posting and public form before and after model latency. The immutable plan hash binds task, posting fingerprint, approval timestamp, schema, full profile-fact snapshot, model metadata and answer content. Freshness is checked inside the shared serialized JSON write queue. Each wording review checks the public form again, then rechecks current local evidence before appending a decision. A replaced plan, changed profile/approval/form or corrupted content cannot receive a fresh approval. These hashes are consistency checks within a trusted local store, not signatures against a malicious local editor.

`ats-answer-plans.json` keeps one latest plan per task, with its review history, in the existing single-process local data directory. Regeneration explicitly replaces that task's previous drafts and decisions; failures preserve them. Delete removes only that plan, not profile facts. Stored narratives are unencrypted candidate data; keep this single-user local prototype off public/multi-user hosting. Execution must independently revalidate evidence and obtain scoped authorization in later increments: `canFill` and `canSubmit` remain false.

### JA-02 optional posting filters

Saved preferences now include optional maximum required years, a desired annual CAD salary minimum, work-mode choices and an explicit keep-unknown policy. Defaults are unset/keep-unknown, including migration from earlier JSON stores. Saving preferences recalculates existing jobs locally and does not change their saved/approved decisions, start a search, or authorize preparation/submission. Collection and source-verification match counts use the same filters.

Every filter returns `match`, `mismatch`, `unknown` or `not_set`, a reason and available source citations. English experience patterns require a recognized requirement section or explicit required/minimum wording; preferred-only/company-history text is not required experience. Recognized independent minimums use their maximum; alternatives, reversed ranges, fractional/unrecognized year wording remain unknown. Salary comparisons require one unambiguous explicitly CAD annual salary amount/range; they do not annualize hourly wages, infer dollars from location, convert currencies, combine bonus/equity, or resolve multiple regional ranges. Passing salary means the advertised range reaches the desired minimum, not a guaranteed offer. Work mode is read only from the source location label, with conflicting labels left unknown. This conservative extractor is not a complete parser or a replacement for Gemini and human JD review.

Unknown-enabled jobs remain in recommendations with a review indication; the user can exclude them. Explicit mismatches leave recommendations but remain in All/saved/approved views. The numeric role/location score stays separate from these checks. No candidate tenure, salary history, work authorization or protected attributes are inferred. Scheduling and real-site application submission remain outside this increment.

### JA-02 source discovery increment

Google Search Grounding is not used for collecting source URLs: its terms prohibit programmatic collection of grounded links for indexing or identifying crawl/scrape targets. Reference: [Google Search Grounding terms](https://ai.google.dev/gemini-api/terms#grounding-with-google-search).

The user agreed to continue with a separate search-provider integration. The first adapter uses Brave Web Search with server-side `BRAVE_SEARCH_API_KEY`. Because discovered URLs are retained, `BRAVE_SEARCH_STORAGE_ALLOWED=true` is additionally required after confirming that the subscribed plan explicitly grants storage rights. This is operator confirmation, not an automatic license check. No account, subscription or paid request was created during development. See [Brave storage-rights guidance](https://brave.com/search/api/) and [Web Search API](https://api-dashboard.search.brave.com/api-reference/web/search/get).

- The editable role/area query defaults to GTA, Toronto, Ottawa and Kingston. Users can search individual GTA municipalities; source search terms are distinct from the saved role/location filters.
- Each click makes one search request (at most 20 results) and at most six public-feed checks, three at a time. No retries, pagination, unattended scheduling or unbounded model search loop. A concurrent source search is rejected.
- Only exact supported HTTPS Greenhouse/Lever hosts and paths become candidates. Arbitrary result URLs, redirects, credentials, nonstandard ports, encoded paths and traversal are not fetched. The existing feed adapters construct their own fixed API URLs.
- Known boards and duplicate board URLs are skipped. Each new source gets a complete-feed check and preference-match count; this is not an assessment of candidate qualifications. Unavailable sources cannot be enrolled through the results UI.
- The latest source search is persisted separately from jobs. Search itself never changes configured boards, imports jobs, approves applications, or prepares resumes. Adding a verified source requires a separate user action, current result ID, an editable company label and a 24-hour result age limit. Enrollment is idempotent and respects the 12-source limit. Normal job collection rechecks the feed.
- A failed search retains the previous results. Changed settings during a request reject its results. Stored match counts are explicitly historical; they do not silently become current scores when preferences change.
- No resume facts, personal contact details or Gemini key are sent to Brave. Only the user's search terms are sent; the UI asks users not to enter personal information. Gemini remains the existing downstream matching/resume provider. Search planning currently uses an editable explicit query, not Gemini query generation.
- Tests replace the search transport and public feeds; real Brave-key acceptance remains outstanding. Broader ATS support, richer eligibility filters and scheduled discovery remain future work.

Verification for this increment: 20 new tests (88 total dashboard tests passing, one live test skipped), dashboard typecheck and production build passed. Browser acceptance exercised the real no-key-disabled state, then intercepted only the browser's API responses with explicitly labeled fixtures to check source discovery, editable labels, successful enrollment and disabled unavailable/already-added actions. Screenshots were inspected at desktop and 390px mobile width (no horizontal overflow). These UI fixtures are not real search/provider evidence. The only console error observed was the pre-existing missing favicon; server error log was empty.

Selecting a role authorizes preparation for that posting. It does not approve unknown answers, invented facts, changed job descriptions, or changed resume bytes. The first real-site release asks for one consolidated final review of the exact document and answers. Subsequent automation can operate under explicitly configured reusable answer policies, while login, MFA, CAPTCHA and unprovided sensitive answers require the user.

On refresh, preserve earlier approved artifacts as history. Never reuse them for a changed posting automatically. On submission timeout, record `submission_uncertain`, inspect receipts or application history, and avoid a second submit until the first outcome is resolved.
